# Интеграция с Java-оркестратором

> Копия от 26 октября 2026 года для репозитория ClawGym. Оригинал — `files/learning-scripts/INTEGRATION.md` в проекте AEFClaw, sha256 `8515df90fe65`. Источник истины — оригинал: копия сама не обновляется.

Что оркестратор должен отправлять агенту и как разбирать ответы, чтобы контур обучения работал. Механику самих скриптов описывает [README.md](README.md), поведение агента — [AGENTS.md](AGENTS.md).

## Исходные условия

- У оператора один диалог с агентом. Рабочие обращения и служебные команды (`/case-capture`, `/skill-curator`, `/reset`) идут в этот же диалог по очереди. Параллельной сессии с доступом к файлам оператора нет.
- Workspace оператора — локальный диск пода AEF Workstation, который периодически выгружается в S3.
- Всё, что оркестратор отправляет агенту, агент видит как сообщение оператора. Служебные команды и их ответы стоит скрывать в интерфейсе оператора или заменять статусом («Агент сохраняет опыт…»).

## Перед выводом

1. Разложить файлы в workspace оператора по структуре из README. `tests/` в workspace не кладётся.
2. Внутри пода, тем же `python3`, которым агент вызывает скрипты, из корня workspace:

   ```
   python3 skills/_learning-lib/doctor.py --init
   ```

   Код 0 — окружение пригодно. Код 3 — в `checks` перечислены ошибки. Предупреждения (`level: warn`) стоит прочитать: например, инфраструктурные файлы, доступные модели на запись.
3. Настроить обвязку из раздела README «Обвязка»: только чтение для инфраструктурных каталогов, ограничение записи, чтения `skills/learned/**` и аргументов `exec`, отключение memory flush. Пройти приёмочный тест прав из того же раздела под реальными правами агента.

## Цикл одного обращения

### 1. Старт обращения

Если в диалоге уже было обращение, сначала `/reset` (как сейчас). Стартовое сообщение агенту, кроме текущих сведений об обращении, должно содержать две строки:

```
Тематика: <тематика обращения в SmartCare>
request_ref: <ref>
```

- **Тематика** — точное название тематики из SmartCare, одинаковое для всех обращений этой тематики. Агент передаёт его в каталог (уроки той же тематики идут первыми) и в capture; по нему считаются метрики.
- **request_ref** — непрозрачная стабильная ссылка на обращение, а не номер обращения. Рекомендуется HMAC-SHA256 от идентификатора обращения с секретом оркестратора, первые 32 hex-символа. Простой SHA-256 от номера обращения восстанавливается перебором. Допустимы также UUID из собственной таблицы соответствий оркестратора и строки `[A-Za-z0-9_.:-]` длиной 6–128 без длинных последовательностей цифр. Одно обращение всегда получает один и тот же ref, в том числе после отложения и повторного открытия: так curator считает кейсы одного обращения одним подтверждением, а не двумя независимыми.

Первым действием агент сам вызовет каталог learned skills и свежих уроков и передаст в него тематику и `request_ref` из этих строк. Это фиксируется в журнале, и в метриках видно, если агент так не сделал. По `request_ref` capture собирает след именно этого обращения: какой каталог агент получил и какие skills прочитал, даже если capture прошлого обращения не завершился.

### 2. Работа оператора с агентом

Без изменений в оркестраторе. Агент теперь иногда задаёт оператору короткий уточняющий вопрос после выполненного поручения («Правильно понимаю: так делаем, потому что…?») — не больше двух за обращение. Ответ оператора становится знанием с условием применения.

Порядок вызова MCP-инструментов и их зависимости надёжнее всего описать прямо в описаниях инструментов, которые отдаёт оркестратор как MCP-сервер: модель видит их в каждом обращении. Общий skill `tool-usage` дополняет их тем, чему оператор учит в работе.

### 3. Конец обращения: capture

Когда обращение закрыто или отложено, отправить в диалог:

```
/case-capture request_ref=<ref> category=<тематика>
```

Дождаться ответа агента и найти в нём строку результата по правилам раздела «Разбор ответа агента и сверка с журналом». Регулярные выражения capture:

```
^Case captured: (\S+) — signal: (strong|medium|weak|none)$
^Case capture skipped: .*$
^Case capture failed: (.*)$
```

| Строка результата | Значение | Что делать |
| --- | --- | --- |
| `Case captured: …` | кейс сохранён; группа 1 — путь, группа 2 — сила знания | учесть сигнал для решения о запуске curator |
| `Case capture skipped: …` | в диалоге не было обращения | ничего |
| `Case capture failed: …` | кейс не сохранён; группа 1 — причина | залогировать причину; обращение для обучения потеряно, работа оператора продолжается |
| строки нет или таймаут | — | сверка с журналом; если события тоже нет — залогировать как сбой capture |

Таймаут рекомендуется измерить на ПРОМе; для начала — 5 минут.

## Когда запускать curator

Раньше поправка оператора становилась доступна агенту только после очередного часового прохода curator. Теперь каждое сохранённое обращение с явной поправкой оператора сразу попадает в **свежие уроки**: агент видит их в начале следующего обращения. Поэтому curator больше не обязан быть частым. Его задача — переносить уроки в learned skills и держать очередь короткой, а запускать его лучше тогда, когда он меньше всего мешает оператору.

Рекомендуемая политика, все пороги — настройки оркестратора:

- запускать только между обращениями, когда у оператора нет открытого обращения: `/reset` → `/skill-curator` → дождаться ответа;
- запускать, если с прошлого прохода сохранено 5 и более кейсов с `signal: strong` или `medium`, или прошло 2 часа при непустой очереди, или начинается перерыв или конец смены (если SmartCare отдаёт статус оператора);
- не перезапускать по признаку `left > 0` без прогресса: если прошлый проход дал `0 processed` и `left` не уменьшился, оставшиеся файлы следующий проход тоже не обработает (например, `blocked` — ошибка доступа к файлу очереди, причина в отчёте). Каждый такой проход холостой и блокирует оператора; следующий запуск — когда появится новый кейс (`Case captured: …`);
- агент показывает не более 10 уроков (переменная `LEARN_LESSONS_MAX` в окружении агента). Если поправок за период между проходами больше, старые уроки перестают показываться до прохода curator, поэтому при большом потоке поправок запускать его чаще.

Разбор ответа curator — по тем же правилам, регулярные выражения:

```
^Curator complete: (\d+) processed, (\d+|\?) left, (\d+) updated, (\d+) routing fixes, (\d+) created, (\d+) conflicts\. Report: (\S+)$
^No pending cases\.$
^Curator failed: (.*)$
```

| Строка результата | Значение |
| --- | --- |
| `Curator complete: …` | проход завершён; группы: обработано, осталось (`?` — остаток не удалось посчитать), обновлено skills, routing-правок, создано, конфликтов, путь отчёта; при `left > 0` следующий проход — при следующей возможности, кроме прохода без прогресса (см. выше) |
| `No pending cases.` | очередь пуста |
| `Curator failed: …` | сбой; следующий `/skill-curator` сам восстановит прерванный проход |

Один проход обрабатывает до 10 кейсов. Длительность прохода стоит измерить на ПРОМе: от неё зависит, сколько оператор ждёт, если откроет обращение во время прохода.

## Разбор ответа агента и сверка с журналом

Строку результата (`result_line`) печатает скрипт, а в чат её переписывает модель. Модель может добавить пояснение до или после неё, обернуть строку в кавычки или обратные апострофы. Поэтому последняя строка ответа ненадёжна.

1. **Искать строку по всему ответу.** Разбить ответ на строки, у каждой обрезать пробелы и символы `` ` `` `"` `'` `«` `»` `*` по краям, применить регулярные выражения команды. Результат — последняя подходящая строка.
2. **Копировать регулярные выражения из блоков кода как есть.** `|` в них — альтернатива, экранирования для таблиц Markdown там нет. В строковом литерале Java обратную косую черту удваивают (`\\d`, `\\S`, `\\.`) или используют text block. В `Case captured` стоит длинное тире (U+2014).
3. **Если строки нет**, в том числе по таймауту, дождаться выгрузки workspace в S3 и проверить в копии журнал `learning/journal/YYYY-MM.jsonl`. Это JSON Lines, одно событие на строку, время в поле `ts`. Нужно событие этой команды с полем `result_line`:

   | Команда | События с `result_line` | Как отличить своё |
   | --- | --- | --- |
   | `/case-capture` | `capture.committed`, `capture.committed_previously`, `capture.reused`, `capture.skipped`, `capture.aborted`, `capture.gave_up` | `request_ref` — ref из команды, `ts` не раньше её отправки. Если команда шла без ref — только по `ts` |
   | `/skill-curator` | `curator.finalized` (с `run_id` прохода), `curator.empty` | `ts` не раньше отправки команды; одновременно идёт только один проход |

   `result_line` события — та же строка, что получил агент. Общий файл «последний результат» не используется: по нему старый результат легко принять за новый.
4. **Если нет ни строки, ни события** — сбой команды. `capture.init` или `capture.invalid` без завершающего события значат, что модель не довела capture до конца. `curator.prepared` без `curator.finalized` — проход прерван, следующий `/skill-curator` его восстановит.

Событие пишется в журнал после самой операции. Если запись не удалась, JSON-ответ скрипта содержит `audit_degraded: true` и список `audit_failed_events`. События в журнале тогда нет, поэтому его отсутствие при найденной строке результата не опровергает результат: строка важнее.

## Выгрузка в S3 и перезапуск пода

- Всё, что записано после последней выгрузки, при перезапуске пода теряется: сохранённые кейсы (а с ними и свежие уроки), правки skills, журнал. Если AEF Workstation позволяет запросить выгрузку, лучше делать это сразу после успешного capture и после завершения curator.
- Если выгрузка поймала curator посреди прохода, после восстановления следующий `/skill-curator` доведёт или закроет прерванный проход: переносы `applying` завершаются, `prepared` закрывается как aborted с отчётом. Уже записанные в этом проходе skills остаются, их кейсы остаются в pending. Единой транзакции на весь проход нет (см. design.md).
- Черновики и резервы capture старше 24 часов удаляются при следующем `/case-capture`.

## Метрики

```
python3 skills/_learning-lib/learning_stats.py --format md
```

Скрипт только читает файлы, поэтому его можно запускать на копии workspace из S3 с `--workspace <путь>`. Главные показатели по тематике и неделе:

- **доля обращений с поправками** — должна снижаться;
- **повторы поправок** — оператор повторил то, что у агента уже было в уроке или skill; должны быть близки к нулю;
- **каталог получен** — ожидается около 100%; если ниже, агент не выполняет поиск skills, и сначала нужно исправлять это.

## Кто за что отвечает

| Оркестратор | Скрипты и агент |
| --- | --- |
| тематика и `request_ref` в стартовом сообщении и в `/case-capture` | каталог, уроки, чтение skills и их фиксация в журнале |
| порядок команд, ожидание завершения, таймауты, поиск строки результата в ответе и сверка с журналом | формат и проверка кейса, обезличивание, evidence policy, `result_line` в ответе и в журнале |
| политика запуска curator | правки skills, переносы кейсов, отчёт, восстановление после обрыва |
| выгрузка в S3, права файловой системы, обвязка из README | проверка окружения (`doctor.py`), метрики (`learning_stats.py`) |
