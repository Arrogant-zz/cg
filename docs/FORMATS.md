# Форматы файлов настроек

Дата: 27 октября 2026 года, обновлено 28 октября. Задача CFG-01 из `gap.md`. Форматы — предложение реализации: владелец задал только состав сущностей и их связи.

Файлы пишутся в YAML; `contracts/tools.json` и шаблоны тела — в JSON. ClawGym проверяет их по схемам из `src/config/schemas.ts`. Неизвестное поле даёт предупреждение и игнорируется, чтобы файлы для следующих версий продолжали загружаться. Ошибка указывает файл, строку, поле, причину и действие. Файлы с именем на `_` не загружаются.

Все файлы лежат в каталоге справочников `config/` (`CLAWGYM_CONFIG`); пути в этом документе считаются от него. Решение владельца от 28 октября 2026 года — README, раздел «Хранение».

Файл, на который ссылается настройка, лежит внутри своего каталога. Ответ заглушки `result.file` — внутри `data/`. Шаблон тела агента `request.body` и шаблон стартового сообщения `startMessage` — внутри каталога справочников. Путь с `..` за пределы каталога или абсолютный путь — ошибка проверки файлов, сам файл не читается и в снимок прогона не попадает.

Идентификаторы: латиница, цифры и `. _ / -`. Ссылки между файлами — по идентификаторам. Секреты — только `${env:NAME}`; значение по умолчанию — `${env:NAME:-значение}`.

## Кейс — `cases/[<папка>/]<id>.yaml`

Ситуация, факты, заглушки инструментов и общий эталон. Поведение оператора в кейсе не хранится. Пример — `cases/spasibo-bonus-missing.yaml`; инструменты — из `tools/list` стенда оркестратора.

Кейсы можно раскладывать по подкаталогам любой глубины, например `cases/cards/disputes/`. Это просьба владельца от 27 октября 2026 года.

- Решения и корзины ссылаются на кейс по `id`, а не по пути: после переноса в папку их править не нужно.
- `id` уникален во всём `cases/`: один `id` в двух папках — ошибка с указанием обоих файлов. Имя файла должно совпадать с `id`, папка в этом не участвует.
- Файл или папка с именем на `_` пропускаются, например `cases/_черновики/`. Так же в `solutions/`.
- В интерфейсе кейсы сгруппированы по папкам, по имени папки работает поиск. Рядом с папкой — число кейсов в ней. Папки сворачиваются, есть «Свернуть все папки». Свёрнутые папки запоминаются в браузере. При поиске и при переходе по ссылке на кейс его папка раскрывается.

```yaml
id: spasibo-bonus-missing             # совпадает с именем файла, иначе предупреждение
title: Не начислены бонусы СберСпасибо
topic: СберСпасибо / Начисление бонусов   # тематика: идёт в /case-capture
tags: [СберСпасибо, Бонусы]
situation: >                          # для людей и оператора; агенту не передаётся
  Клиент 12 октября купил товар у партнёра и не получил бонусы…
start: {}                             # необязательно: поля {{start.*}} для шаблона старта
facts:                                # факты, на вопросы о которых оператор может отвечать
  - Партнёр подтверждает покупки в течение 30 дней.
state:                                # начальное состояние выполнения: {{state.*}}, меняется effect
  case: open
tools:                                # заглушки по имени инструмента
  get_static_attributes_assigned:     # ответы этих заглушек подставляются и в стартовое сообщение: {{tools.<имя>}}
    - id: static                      # имя видно в журнале; по умолчанию <tool>#<n>
      result:
        json: { classifier: { categoryName: СберСпасибо / Начисление бонусов } }
  get_spasibo_history_info:
    - id: history
      when: { dateFrom: "2026-10-01" }   # подмножество аргументов
      result:
        json: { operations: [{ date: "2026-10-12", bonus: 249, status: PENDING_PARTNER_CONFIRMATION }] }
  get_close_with_answer:
    - id: closed
      delayMs: 600
      result: { json: { status: CLOSED } }
      effect: { case: closed }        # изменение состояния этого выполнения
  create_expertise:
    - sequence:                       # ответы на последовательные вызовы, последний повторяется
        - result: { file: expertise/created.json }   # файл из data/
        - error: { message: already_exists, code: EXPERTISE_EXISTS }
reference:                            # общий эталон; агенту не передаётся
  procedure: [Запросить основную информацию Спасибо, Проверить историю операций СберСпасибо, …]
  answer: Бонусы ожидают подтверждения партнёром и будут начислены после него.
  finalClass: close_answer            # M1: класс финального действия
  tools: [get_spasibo_general_info, get_spasibo_history_info, get_close_with_answer]   # M2: эталон F1_tools
  # finalText: …                      # M2: эталонный итоговый текст для A_judge; не задан — берётся answer
  criteria:                           # для LLM-оценки
    - id: pending
      text: Сообщает, что бонусы ожидают подтверждения покупки партнёром
      lesson: L-spasibo-005           # урок, к которому относится критерий
      hint: ожидают подтверждения     # подсказка только для dev/fake-gigachat (models: devHints)
  actions:                            # для автоматических проверок
    required:
      - tool: get_spasibo_history_info
        before: get_close_with_answer # порядок
        lesson: L-spasibo-004
        args: { dateFrom: "2026-10-01" }   # необязательные условия на аргументы
    forbidden:
      - tool: create_expertise
    final: get_close_with_answer      # итоговое действие должно быть выполнено
  lessons:                            # каталог известных уроков кейса (MET-04)
    - id: L-spasibo-004
      rule: Перед ответом проверить историю операций СберСпасибо за период покупки.
```

**Эталон для метрик аналитика M1 и M2** (решение владельца от 27 октября 2026 года применять документ аналитика):

| Поле | Значение |
| --- | --- |
| `finalClass` | Класс финального действия: `close_answer` — ответ клиенту и закрытие, `expertise` — экспертиза, `request_info` — запрос информации у клиента, `operator_instruction` — инструкция оператору. Не задан — выводится из `actions.final` по соответствию в метрике `final-action`; не выводится — кейс не входит в M1 |
| `tools` | Минимально достаточный набор инструментов по эталонному сценарию: не «всё, что вызывал оператор». Элемент — имя или `{ tool, count }`, если нужно несколько вызовов. Не задан — F1 и M2 для кейса не считаются |
| `finalText` | Эталонный итоговый текст для A_judge того же вида, что финал: ответ клиенту, описание экспертизы или инструкция оператору. Не задан — берётся `answer` |

Эталон берётся не из навыка агента: из истории операторов или разметки эксперта.

**Условия в `when`:**

| Запись | Значение |
| --- | --- |
| Значение | Равенство; числа и строки сравниваются как строки |
| `{ regex: "^OP-" }` | Регулярное выражение JavaScript с флагом `u`: например, дефис в классе символов ставится последним — `[\w.-]`. Выражение проверяется при загрузке; невалидное — ошибка с полем и строкой, прогон с таким кейсом не запускается. Проверка одного выражения на аргументе ограничена 100 мс: если перебор дольше, как у `^(a+)+$`, проверка прерывается, условие не выполнено, а в журнале процесса — предупреждение. Так выражение не останавливает стенд |
| `{ in: [a, b] }` | Одно из значений |
| `{ exists: true }` | Аргумент задан |
| `{ not: x }` | Не равно |
| `request.channelCode` | Вложенный аргумент |

Из подходящих заглушек выбирается та, у которой больше условий. Если в кейсе подходящей заглушки нет, поиск продолжается в `contracts/tool-defaults.yaml`.

**Ответ:** ровно одно из `result.json`, `result.text`, `result.file` — или `error` (строка либо `{ message, code }`). `result.file` — путь внутри `data/`. Дополнительно можно задать `delayMs` и `effect`:

- `delayMs` — задержка ответа агенту;
- `effect` — изменения состояния выполнения: ключ — путь в `state` через точку, значение — с подстановками. Имена `__proto__`, `constructor` и `prototype` в пути — ошибка проверки файлов. Эффект применяется, когда ответ уходит агенту, то есть после `delayMs`. Если выполнение остановлено во время задержки, вызов не выполнен и состояние не меняется.

**Шаблоны в строках:**

| Шаблон | Что подставляется |
| --- | --- |
| `{{case.*}}` | Поля кейса |
| `{{start.*}}` | Стартовые данные |
| `{{args.*}}` | Аргументы вызова |
| `{{state.*}}` | Состояние выполнения |
| `{{execution.taskId}}` | x-task-id выполнения; в оркестраторе он же `request_ref` |
| `{{execution.caseNumber}}`, `{{execution.requestRef}}` | Номер обращения и `request_ref` по INTEGRATION.md |
| `{{now}}` | Текущее время |

## Решение — `solutions/<кейс>/<имя>.yaml`

Сценарий LLM-оператора для кейса. Идентификатор по умолчанию — путь без `solutions/` и расширения, например `spasibo-bonus-missing/explain-now`.

```yaml
case: spasibo-bonus-missing
title: «Объясняет сразу»
goal: усвоит ли агент правило, если его сразу объяснили.
operator:
  instruction: >                      # главное для LLM-оператора
    Отклоняй действия, которые расходятся с эталоном, и сразу объясняй правило.
  style: explain-now                  # необязательная метка; утверждённого перечня режимов нет
  seesToolResults: true               # видит ли оператор ответы инструментов (по умолчанию да)
  lessons: []                         # дополнительные уроки к каталогу кейса
limits: { maxTurns: 20 }              # переопределение лимитов прогона
```

## Корзина — `baskets/<id>.yaml`

```yaml
id: second-line-train
title: Обучение · СберСпасибо и операции по картам
type: training                        # training | checking; смешивать нельзя
curator:                              # только training; без блока curator не запускается
  every: 2                            # каждые N завершённых решений; 0 — без периодических
  final: true                         # дополнительный проход в конце неполной пачки
  resetBefore: true                   # /reset перед /skill-curator (по умолчанию да)
checking:                             # только checking
  confirmations: approve              # approve — без вмешательства оператора; operator — решает LLM
items:                                # фиксированный порядок; решение может повторяться
  - solution: spasibo-bonus-missing/explain-now
    limits: { maxTurns: 12 }          # параметры конкретного элемента
  - curator: true                     # явный шаг curator (только training)
```

В проверяющей корзине блок `curator` с проходами и шаги `curator` — ошибка.

## Настройка прогона — `runs/<id>.yaml`

```yaml
id: demo-train
title: Обучение · вторая линия · fake-agent
basket: second-line-train             # тип прогона берётся из корзины
agent: fake-agent
models:
  operator: fake-operator             # обязательно
  judge: fake-judge                   # без неё ответ «не оценён»
# continueFrom: demo-train            # продолжить на тестовом операторе последнего завершённого прогона этой настройки
metrics: all                          # или список идентификаторов из metrics/
limits: { maxTurns: 20, maxDurationSec: 900, maxOperatorCalls: 30 }
repetitions: 1                        # независимые линии, у каждой свой тестовый оператор
startAt: 2026-10-27T01:00:00+03:00    # необязательное время старта
```

**Тестовый оператор** (решение владельца от 27 октября 2026 года). Модель агента, его стартовые и выученные скиллы живут внутри агента у тестового оператора — `x-a2a-sender-id`. ClawGym их не устанавливает и не выгружает.

- Без `continueFrom` прогон идёт на новом операторе со стартовыми скиллами сборки.
- С `continueFrom` — на операторе последнего завершённого или остановленного прогона указанной настройки, с выученными там скиллами.

Условия продолжения:

- тот же агент;
- число повторений не больше числа линий у того прогона — линия N продолжает линию N;
- на операторе не идёт другой прогон или ручная сессия.

При запуске выбор можно переопределить: `overrides.continueFrom` в API — номер прогона или `new`, ключ `--continue` в CLI.

## Агент — `agents/<id>.yaml`

Реальное подключение — `agents/aef-claw.yaml`, тестовое — `agents/fake-agent.yaml` с тем же форматом запроса и ответа.

```yaml
id: aef-claw
title: AEFClaw
request:
  url: ${env:AEF_CLAW_URL:-http://127.0.0.1:18789/a2a}
  method: POST
  headers: { a2a-version: "1.0" }     # токен шлюза, если нужен: Authorization: ${env:AEF_CLAW_AUTHORIZATION}
  body: templates/aefclaw-a2a-message.json   # файл внутри config/ или объект; {{text}}, {{taskId}}, {{senderId}}, {{messageId}}
  textPath: $.params.message.parts[0].text   # необязательно: вместо {{text}} в шаблоне
  taskIdHeader: x-task-id
  senderIdHeader: X-A2A-Sender-Id
  taskIdScope: execution              # execution | message
  timeoutMs: 900000
response:
  mode: sync                          # реализован только sync
  replyPath: $.result.task.status.message.parts[*].text
  statusPath: $.result.task.status.state
  errorPath: $.error.message          # JSON-RPC error
  usage: { inputPath: …, outputPath: …, totalPath: … }   # у AEFClaw путь неизвестен — «нет данных»
commands:                             # по умолчанию — тексты из INTEGRATION.md
  reset: /reset
  capture: /case-capture request_ref={{taskId}} category={{topic}}   # {{taskId}} — x-task-id стартового сообщения; {{requestRef}} — HMAC по INTEGRATION.md
  curator: /skill-curator
mcp: { contract: contracts/tools.json }   # x-task-id и версию протокола MCP-сервер выбирает сам для всех агентов — CONTRACTS.md, раздел 4
model: задана развёртыванием AEFClaw   # метка для снимка и сравнения: модель задаёт сборка, ClawGym её не переключает
sessions: { max: 3 }
healthUrl: ${env:AEF_CLAW_HEALTH_URL:-http://127.0.0.1:18789/readyz}   # без него доступность «не проверяется»
build: метка сборки
learningKit: версия комплекта обучения
```

Подробности и статус каждого поля — в [CONTRACTS.md](CONTRACTS.md).

## Модель — `models/<id>.yaml`

Решение владельца от 27 октября 2026 года: модели оператора и оценки — только GigaChat; провайдеры OpenAI и Anthropic убраны. Тестовые `fake-operator` и `fake-judge` — тот же GigaChat API на `dev/fake-gigachat`.

```yaml
id: op-gigachat
roles: [operator]                     # operator | judge
provider: gigachat-v1                 # gigachat-v1 | gigachat-v2
baseUrl: ${env:GIGACHAT_BASE_URL}
model: ${env:GIGACHAT_OPERATOR_MODEL:-GigaChat-2-Max}
params:
  temperature: 0.3                    # GigaChat принимает только больше 0
  maxTokens: 4000
  timeoutMs: 120000
  retries: 2                          # повторы при 429, 5xx и сетевых сбоях
  responseFormat: json_schema         # json_schema | none
  devHints: false                     # только для dev/fake-gigachat
```

Модели агента в `models/` нет: её задаёт сборка агента, а в подключении — только метка `model`. Ответы оператора и судьи проверяются по JSON-схеме; при ошибке формата модель переспрашивается один раз.

### GigaChat — `gigachat-v1` и `gigachat-v2`

Формат — по OpenAPI-спецификации GigaChat API на developers.sber.ru, прочитанной 26 октября 2026 года. С настоящим GigaChat не проверялся. Пример — `models/op-gigachat.yaml` (v1) и `models/judge-gigachat.yaml` (v2). Остальные поля модели: `path` — путь метода, если шлюз отличается; `apiKey` — токен в `Authorization`; `headers`.

```yaml
id: judge-gigachat
roles: [judge]
provider: gigachat-v2                 # gigachat-v1 — POST {baseUrl}/v1/chat/completions; gigachat-v2 — POST {baseUrl}/v2/chat/completions
baseUrl: ${env:GIGACHAT_BASE_URL}     # корень API без версии: https://gigachat.devices.sberbank.ru/api или http://… внутри Istio
path: /v2/chat/completions            # необязательно: другой путь, если его требует шлюз контура
model: ${env:GIGACHAT_JUDGE_MODEL:-GigaChat-2-Max}
tls:                                  # необязательно
  cert: ${env:GIGACHAT_CERT_FILE:-}   # клиентский сертификат, PEM; пусто — вызов без сертификата
  key: ${env:GIGACHAT_KEY_FILE:-}     # закрытый ключ, PEM
  # pfx: ${env:GIGACHAT_PFX_FILE:-}   # или сертификат с ключом в PKCS#12 — вместо cert и key
  passphrase: ${env:GIGACHAT_KEY_PASSPHRASE:-}
  ca: ${env:GIGACHAT_CA_FILE:-}       # корневой сертификат сервера, если его нет в хранилище Node.js
params:
  temperature: 0.01                   # GigaChat принимает только больше 0
  maxTokens: 4000
  timeoutMs: 120000
  retries: 2
  responseFormat: json_schema         # json_schema | none
```

- **Авторизация** — клиентский сертификат (mTLS), если заданы его файлы. Файлы читаются при каждом вызове: новый сертификат подхватывается без перезапуска.
- **Без сертификата** — если файлы не заданы, ClawGym вызывает адрес как есть. Так работает установка внутри Istio: `baseUrl` — http-адрес внутри сетки, а mTLS до GigaChat делает sidecar или egress-шлюз. Решение владельца от 26 октября 2026 года. Http без сертификата используйте только внутри сетки: иначе запросы к модели идут без шифрования.
- **Сертификат задаётся целиком:** `tls.cert` и `tls.key` вместе или один `tls.pfx`. Только по https: сертификат вместе с http-адресом — ошибка настройки, а не тихий отказ от mTLS. Только `tls.ca` — для https без клиентского сертификата.
- **Токен.** Заголовок `Authorization: Bearer …` добавляется, только если задан `apiKey`; получение токена OAuth не реализовано.
- **Сертификат сервера.** Если сертификат сервера выдан центром, которого нет в хранилище Node.js, укажите `tls.ca`, например, корневой сертификат НУЦ Минцифры. Другой вариант — переменная `NODE_EXTRA_CA_CERTS`.
- **Запрос v1:** `messages` из строк `system` и `user`, `temperature`, `max_tokens`, `stream: false`, `response_format`.
- **Запрос v2:** части `content: [{ text }]`, параметры — внутри `model_options`.
- **Структурированный ответ** — `response_format: { type: json_schema, schema, strict: true }`, схема без обёртки OpenAI. Если GigaChat отклонит схему (HTTP 422), задайте `responseFormat: none`: ответ всё равно проверяется, при ошибке формата модель переспрашивается.
- **Ответ:**
  - текст берётся из `choices[0].message.content` (v1) или из частей `messages[].content[].text` (v2);
  - токены — из `usage`;
  - `finish_reason: length` — обрезка ответа;
  - `blacklist` и другие срабатывания фильтра — отказ модели.
- **Трассировка.** Каждый вызов получает свой `X-Request-ID`; он попадает в текст ошибки, чтобы найти запрос в журналах GigaChat. Дополнительные заголовки, например `X-Client-ID`, задаются в `headers`.
- **Ошибки сертификата** объясняют, что исправить: нет `tls.ca`, сервер не принял клиентский сертификат, ключ не подходит или неверен пароль. Такие ошибки не повторяются.

## Метрики — `metrics/*.yaml`

Файл с одной метрикой или списком `metrics:`. Каждая метрика выбирает встроенный расчёт:

```yaml
metrics:
  - id: success
    builtin: success                  # см. ниже
    title: Итоговый успех
    description: …
    level: [кейс, корзина]
    needs: обе проверки
    version: v1
```

Встроенные расчёты:

| Расчёт | Что считает |
| --- | --- |
| `action-checks` | Проверки действий |
| `answer-quality` | Качество ответа |
| `success` | Итоговый успех |
| `corrections` | Поправки |
| `repeated-corrections` | Повторные поправки |
| `rejected-actions` | Отклонённые действия |
| `unexpected-tools` | Неожиданные инструменты |
| `turns-duration` | Ходы и длительность |
| `tokens` | Токены |
| `operator-errors` | Сбои LLM-оператора |
| `final-action` | M1: macro-F1 по классам финального действия, accuracy, матрица ошибок |
| `tools-f1` | F1 вызовов инструментов по эталонному набору |
| `answer-match` | A_judge: соответствие итогового текста эталонному |
| `case-score` | M2: среднее case_score = w_tools · F1_tools + w_answer · A_judge |

Нет данных — «нет данных» с причиной, а не ноль. Параметры входят в определение метрики: прогоны с разными параметрами сравнение покажет как несопоставимые.

### Метрики аналитика: M1 и M2

Источник — документ «Аналитика оценки качества обучения агента» (ред. 22.10.2026), который владелец 27 октября 2026 года решил применять. Схема: тестовый датасет до обучения, обучение, тот же датасет после; сравниваются ΔM1 = M1_после − M1_до и ΔM2. Сводить M1 и M2 в одно число не нужно. Параметры по умолчанию — в `metrics/builtin.yaml`; ошибка в параметрах видна при загрузке, прогон с ней не запустится.

**M1 — `final-action`.** Класс агента — по последнему выполненному вызову инструмента из `params.classes`. Отклонённый оператором вызов кейс не завершает. Без такого вызова при обычном завершении класс — `operator_instruction`, итоговый текст — последняя реплика агента. Лимит без итогового действия или технический сбой — кейс незавершённый: в M1 не входит и считается отдельно. Macro-F1 — среднее F1 по классам, которые есть в эталоне или в ответах агента.

```yaml
params:
  classes:
    close_answer: [get_close_with_answer]
    expertise: [create_expertise]          # элемент — имя или { tool, args } с условиями как в when
    request_info: []                       # в tools/list стенда инструмента нет
    operator_instruction: []
```

**F1_tools — `tools-f1`.** TP — инструменты в ответе ∩ эталон, FP — лишние, FN — пропущенные; F1 = 2TP / (2TP + FP + FN). Порядок вызовов не важен. Считаются все вызовы агента до служебных команд, включая отклонённые.

| `duplicates` | Правило |
| --- | --- |
| `tolerate` (по умолчанию) | Повторы схлопываются: до `maxRepeats` вызовов инструмента — как один; каждый следующий — FP. Затем формула аналитика: TP = min(p, r), FP = max(0, p − r), FN = max(0, r − p) |
| `strict` | Формула аналитика без схлопывания: каждый вызов сверх эталона — FP |
| `whole` | Альтернатива из документа: сверх допустимого весь инструмент — FP, нужные вызовы — FN |

`ignore` — инструменты, которые не считаются ни верными, ни лишними.

**A_judge — `answer-match`.** Судья (`judge` в прогоне) `runs` раз независимо сравнивает итоговый текст агента с эталонным и отвечает «соответствует» или нет; A — доля прогонов «соответствует», при трёх прогонах 0, ⅓, ⅔ или 1. Итоговый текст — первое непустое поле аргументов итогового вызова из `params.text`; для классов без путей — последняя реплика агента. Пустой итоговый текст — A = 0 без вызова судьи. Сбой любого прогона — A нет: градация держится на полном числе прогонов. Подсказка судьи — `answer-judge-v1`, её версия сохраняется в прогоне.

**M2 — `case-score`.** case_score = w_tools · F1_tools + w_answer · A_judge, `params.weights` с суммой 1: стартовые 0.5 и 0.5, если важнее ответ клиенту — 0.4 и 0.6. M2 — среднее по кейсам, где есть обе части. Судья по эталонному тексту вызывается, только если в прогоне выбрана `answer-match` или `case-score`.

Результаты по кейсу — в событии `scores` журнала и в поле `scores` элемента прогона. Итог кейса «пройден / не пройден» они не меняют.

## Контракт — `contracts/`

- `tools.json`:
  - `tools[]` — поля MCP как в `tools/list` оркестратора: `name`, `title`, `description`, `inputSchema`, `annotations` (`outputSchema`, `_meta` — если есть); агенту они отдаются без изменений;
  - пометки ClawGym в том же объекте, агенту не отдаются: `requiresConfirmation`, `kind` (`info` | `action`), `enabled`, `terminal`;
  - список снимается со стенда командой `import-tools`: поля MCP обновляются, пометки ClawGym сохраняются (README, раздел CLI);
  - `result.mode` — `text` | `structured` | `both`;
  - `errors` — тексты для агента с `{{tool}}`. `closed` — ответ на вызов с подтверждением после закрытия кейса терминальным инструментом. Если его нет, используется «Обращение уже закрыто: инструмент {{tool}} недоступен.»;
  - `conditional: true` — контракт ещё не сверен с оркестратором.
- `enabled: false` у инструмента — выключить его, не удаляя описание. Решение владельца от 26 октября 2026 года. Что при этом происходит:
  - инструмента нет в `tools/list`;
  - его вызов получает ошибку `unknownTool`, а в журнале кейса — пометку «выключен в контракте»;
  - заглушки кейсов остаются и доступны шаблону стартового сообщения.
- `terminal` у инструмента — терминальный инструмент: выполненный вызов закрывает кейс. Решение владельца от 28 октября 2026 года. Значения:
  - `true` — любой выполненный вызов;
  - `{ "when": { … } }` — только вызов, аргументы которого подходят под условие. Язык условий тот же, что у `when` заглушек: равенство (числа и строки сравниваются как строки), `regex`, `in`, `exists`, `not`, вложенные аргументы через точку. Если аргумента нет, равенство не выполнено: `change_stage` без `keepOnSelf` не терминальный, обратное задаётся `{ "not": true }`;
  - `false` или поля нет — инструмент не терминальный.

  Выполненный вызов — разрешённый или не требующий подтверждения, с ответом заглушки или человека без ошибки. Отклонённый вызов и ответ-ошибка кейс не закрывают. Что происходит после закрытия — `CONTRACTS.md`, правило 21. Пример:

  ```json
  { "name": "change_stage", "requiresConfirmation": true, "terminal": { "when": { "request.keepOnSelf": false } } }
  ```
- `start-message.txt` — шаблон стартового сообщения. Строка, где подстановка оказалась пустой, выпадает целиком. Объект подставляется компактным JSON. Доступны:
  - `{{case.id}}`, `{{case.title}}`, `{{case.topic}}`, `{{start.<поле>}}` — данные кейса;
  - `{{execution.taskId}}` — x-task-id, с которым уйдёт стартовое сообщение; в оркестраторе `request_ref` равен ему;
  - `{{execution.caseNumber}}`, `{{execution.requestRef}}` — номер обращения и request_ref по INTEGRATION.md;
  - `{{tools.<инструмент>}}` — ответ заглушки инструмента из кейса, или `{{tools.<инструмент>.<путь>}}` — поле ответа. Заглушка выбирается как для вызова без аргументов; берётся первый ответ последовательности, эффект не применяется. Поэтому агент при своём вызове получит тот же ответ.
- Пример в формате оркестратора (`TaskService.processTask`):

  ````text
  <текст промпта из конфигурации оркестратора>
  ```
      Тематика: {{tools.get_static_attributes.classifier.categoryName}}
      request_ref: {{execution.taskId}}
  ```.
  Результат вызова инструмента «Получение кейса для сотрудника»{{tools.get_assigned_case}}.
  Результат вызова инструмента «Получение статических атрибутов кейса»{{tools.get_static_attributes}}
  ````

  Имена инструментов здесь условные: возьмите имена из контракта. На странице кейса есть предпросмотр «Стартовое сообщение — как его получит агент».
- `tool-defaults.yaml`: `tools:` — заглушки по умолчанию в формате кейса.
