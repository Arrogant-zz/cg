# ClawGym

Тестовый стенд обучения агента Pagurus. ClawGym заменяет для агента Java-оркестратор:
- вызывает агента по REST;
- сам является его MCP-сервером: инструменты отвечают заглушками кейса;
- играет оператора с помощью LLM или даёт пройти кейс вручную;
- отправляет служебные команды `/reset`, `/case-capture`, `/skill-curator`;
- оценивает результат автоматическими проверками действий и отдельной LLM-оценкой, считает метрики аналитика M1 и M2;
- прогоняет обучающие и проверяющие корзины на тестовых операторах агента, считает метрики и сравнивает прогоны до и после обучения.

Требования и задачи — в документах проекта AEFClaw: `gap.md` (задачи первой автоматической версии), `plan.md`, `plan_start.md`. Интерфейс сделан по канвасу «ClawGym — дизайн интерфейса» и стилю `ui/style-guide.md`.

**Статус на 27 октября 2026 года.** Реализация проверена только офлайн, на `dev/fake-agent` и `dev/fake-gigachat`: сквозные и модульные тесты, ручной проход интерфейса в браузере. С настоящими AEFClaw и GigaChat не запускалась. Метрики аналитика M1 и M2 посчитаны только на fake-моделях; судья по эталонному тексту на GigaChat не калибровался.

**Хранение.** Справочники и настройки лежат в `config/` (`CLAWGYM_CONFIG`). Результаты прогонов и ручные сессии — в `var/` (`CLAWGYM_VAR`). Пути вида `cases/…`, `runs/…`, `agents/…` в этом файле, в `docs/` и в интерфейсе считаются от `config/`. Подробности — раздел «Хранение».

Что уже взято со стенда оркестратора:
- инструменты MCP — `tools/list`, расшифрованный с фото, возможны опечатки; точный список снимается командой `import-tools`;
- формат запроса к AEFClaw — `templates/aefclaw-a2a-message.json` и `agents/aef-claw.yaml`;
- формат стартового сообщения — `contracts/start-message.txt`.

Обёртка результата инструментов, тексты ошибок и список инструментов с подтверждением пока условные: [docs/CONTRACTS.md](docs/CONTRACTS.md). Что доделать во внутреннем контуре — [CLI_plan.md](CLI_plan.md).

## Быстрый старт

Нужен Node.js 20.3 или новее (с этой версии есть `AbortSignal.any`); лучше актуальный LTS (22 или 24).

```bash
npm ci
```

```bash
npm run build
```

Локальный стенд одной командой: ClawGym на `:8080`, fake-agent на `:8091`, fake-gigachat на `:8092`. Fake-agent говорит на том же A2A, что AEFClaw, и вызывает инструменты стенда оркестратора; fake-gigachat играет LLM-оператора и судью в формате GigaChat API.

```bash
npm run demo
```

Откройте http://127.0.0.1:8080 и проверьте путь из примера:

1. «Запуск прогона» → «Проверка · вторая линия · новый оператор» → «Запустить прогон». Это проверка до обучения: новый тестовый оператор начинает со стартовых скиллов сборки fake-agent.
2. «Обучение · вторая линия · fake-agent» → «Запустить прогон». Обучение идёт на кейсах СберСпасибо, оспаривания операции и заблокированной суммы по карте. Выученное остаётся у тестового оператора в агенте.
3. На странице обучающего прогона нажмите «Проверить на этом операторе». Та же проверка пойдёт на обученном операторе; файл `demo-check-trained` делает то же самое по умолчанию.
4. «Сравнение» покажет, что условия различаются только тестовым оператором, ΔM1 и ΔM2 и какие кейсы стали лучше. В демо M1 растёт с 0,73 до 1,00, M2 — с 0,44 до 0,96: см. «Метрики аналитика M1 и M2».
5. «Ручной режим» → кейс `notifications-channel-change`. Для `get_smsbank_notifications` заглушки нет: ответьте вместо инструмента (Cmd/Ctrl+Enter), затем решите подтверждение `change_notifications_channel_for_case`. Реплика уходит по Enter, Shift+Enter переносит строку. Когда вы разрешите `get_close_with_answer`, кейс закроется: это терминальный инструмент. Реплики после этого не принимаются, а `/case-capture`, `/skill-curator` и «Завершить и сохранить» остаются; `/reset` начинает кейс заново.
6. Во вкладке «HTTP-обмены» сессии или кейса видны все запросы к агенту и запросы агента к MCP — см. «Журнал HTTP-обменов».

Прогоны, сделанные до 27 октября, собраны на версиях наборов скиллов, от которых тогда отказались (раздел «Тестовый оператор»). Они по-прежнему открываются, в подписи тестового оператора указан набор. Для чистого демо `var/` можно удалить.

Тесты работают офлайн: сборка, сквозные сценарии на fake-agent и fake-gigachat, модульные тесты. Тесты GigaChat создают временные сертификаты через `openssl`; без него они пропускаются.

```bash
npm test
```

Проверка файлов настроек без запуска сервиса:

```bash
npm run validate
```

## Подключение к стенду

1. Снимите точный список инструментов с MCP оркестратора — команда `import-tools` (раздел CLI). Остальные условные пункты — [docs/CONTRACTS.md](docs/CONTRACTS.md).
2. Направьте MCP агента в AEFClaw на `http://<хост ClawGym>:8080/mcp`. Если MCP нужно вынести на отдельный порт, задайте `MCP_PORT`: там будут доступны только MCP и `/health`.
3. Задайте переменные окружения подключения и моделей. Секреты задаются только окружением; в файлах настроек — ссылки вида `${env:NAME}`.

| Переменная | Назначение |
| --- | --- |
| `AEF_CLAW_URL` | Полный адрес A2A агента AEFClaw (`agents/aef-claw.yaml`), по умолчанию `http://127.0.0.1:18789/a2a` |
| `AEF_CLAW_HEALTH_URL` | Проверка доступности агента, по умолчанию `http://127.0.0.1:18789/readyz` |
| `AEF_CLAW_AUTHORIZATION` | Токен шлюза, если он нужен: раскомментируйте `Authorization` в `agents/aef-claw.yaml` |
| `AGENT_ALLOWED_HOSTS` | Белый список хостов агента через запятую, например `stand.local,.stand.local`. Адрес вне списка отклоняется: стенд нельзя направить на ПРОМ |
| `GIGACHAT_BASE_URL` | Корень GigaChat API без версии для `models/op-gigachat.yaml` (v1) и `models/judge-gigachat.yaml` (v2): `https://gigachat.devices.sberbank.ru/api` или http-адрес внутри Istio |
| `GIGACHAT_CERT_FILE`, `GIGACHAT_KEY_FILE` | Клиентский сертификат и ключ GigaChat (PEM) для mTLS. Необязательны: внутри Istio задайте только http-адрес, сертификат подставит сетка |
| `GIGACHAT_KEY_PASSPHRASE`, `GIGACHAT_CA_FILE` | Пароль ключа и корневой сертификат сервера — если нужны |
| `GIGACHAT_OPERATOR_MODEL`, `GIGACHAT_JUDGE_MODEL` | Имена моделей; по умолчанию `GigaChat-2-Max` |
| `AGENT_MCP_TIMEOUT_MS` | Таймаут MCP-вызова, настроенный в агенте. По нему считаются обратный отсчёт и срок решения оператора; по умолчанию 600000 |

4. Запустите схему аналитика: `runs/stand-check.yaml` → `runs/stand-train.yaml` → `runs/stand-check-trained.yaml`. Это AEFClaw, оператор и оценка на GigaChat. Первая проверка идёт на новом тестовом операторе со стартовыми скиллами сборки, вторая — на операторе обучения. Сравните первую и третью.

## Сборка образа

Dockerfile по решению владельца делает владелец. Что нужно знать для образа:

- Сборка: `npm ci`, затем `npm run build`, затем `npm prune --omit=dev`. Зависимостей во время работы две: `ajv` и `yaml`.
- В `package-lock.json` указан `registry.npmjs.org`: npm подменит его на реестр из `.npmrc` контура.
- Запуск: `node dist/src/main.js`. В образе нужны каталоги `dist/`, `node_modules/` и `web/`. Справочники `config/` кладутся в образ или приходят томом.
- Порт `PORT` (по умолчанию 8080): интерфейс, API, SSE и MCP. Если задан `MCP_PORT`, MCP доступен ещё и на нём.
- Проверка живости: `GET /health`.
- Справочники (`CLAWGYM_CONFIG`) и данные (`CLAWGYM_VAR`) — два разных каталога, их монтируют отдельными томами. Данные должны пережить перезапуск пода. Что где лежит и как синхронизировать каталоги с S3 — раздел «Хранение».
- Внешние CDN и шрифты не нужны: шрифты IBM Plex лежат в `web/fonts` (лицензия SIL OFL 1.1).

## Доступ к стенду

Входа в интерфейс нет; нужен ли он — открытый вопрос `plan.md`, раздел 10. Пока доступ закрывают сетью: политикой Istio (`AuthorizationPolicy`) или ingress с авторизацией. Кто открыл интерфейс, тот может запускать и удалять прогоны и видит журналы.

От межсайтовых запросов API защищён сам:
- `POST` принимается только с заголовком `Content-Type: application/json`, иначе ответ 415. С чужой страницы браузер отправит такой запрос только после `OPTIONS`, а ClawGym его не разрешает. Поэтому страница, открытая у сотрудника с доступом к стенду, не запустит прогон и не напишет в ручную сессию.
- `DELETE` без разрешающего ответа на `OPTIONS` браузер не отправляет и так.
- У MCP-адреса такой проверки нет: его вызывает агент, а MCP-клиент AEFClaw ещё не сверен.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT`, `HOST` | `8080`, `0.0.0.0` | Адрес сервиса |
| `CLAWGYM_CONFIG` | `config` | Справочники и настройки: кейсы, решения, корзины, прогоны, агенты, модели, метрики, контракт, шаблоны |
| `CLAWGYM_VAR` | `var` | Результаты прогонов, ручные сессии, счётчики номеров, секрет `request_ref` |
| `CLAWGYM_WEB` | `web` | Статика интерфейса |
| `MCP_PATH`, `MCP_PORT` | `/mcp`, не задан | Адрес MCP-сервера; отдельный порт — по желанию |
| `MCP_TASK_ID_HEADER` | `x-task-id` | Где MCP ищет привязку вызова: заголовок, затем `_meta`, затем аргумент |
| `MCP_RESPONSE_MODE` | `json` | `sse` — отвечать на `tools/call` событием SSE, если клиент его принимает |
| `AGENT_ALLOWED_HOSTS` | `localhost,127.0.0.1,::1` | Белый список хостов агента; `.domain` разрешает поддомены |
| `SENDER_PREFIX` | `lab-` | Префикс `x-a2a-sender-id` тестовых операторов |
| `AGENT_MCP_TIMEOUT_MS` | `600000` | Таймаут MCP-вызова в агенте |
| `OPERATOR_DECISION_MARGIN_MS` | `30000` | Запас: LLM-оператор решает по подтверждению за `AGENT_MCP_TIMEOUT_MS` минус запас, иначе вызов отклоняется как технический сбой |
| `TURN_TIMEOUT_MS` | `900000` | Таймаут ответа агента на реплику |
| `RESET_TIMEOUT_MS`, `CAPTURE_TIMEOUT_MS`, `CURATOR_TIMEOUT_MS` | `120000`, `300000`, `900000` | Таймауты служебных команд |
| `AGENT_BUSY_WAIT_MS` | `900000` | Сколько следующий запрос тестовому оператору ждёт в очереди агента за прерванным: ClawGym перестал ждать ответа, а агент продолжает ход. Раздел «Прерванный ход» |
| `UNMATCHED_MODE` | `manual` | Ручной режим без заглушки: `manual` — ждать ответа человека, `error` — сразу ошибка. В автоматическом прогоне всегда ошибка |
| `MAX_PARALLEL_SESSIONS` | `2` | Одновременные сессии агента: линии прогонов и ручные кейсы. Стенд выдерживает 2–3 |
| `REQUEST_REF_SECRET` | генерируется и хранится в `$CLAWGYM_VAR/secret.json` | Секрет HMAC для `request_ref` |
| `LOG_LEVEL` | `info` | `debug`, `info`, `warn`, `error` |

Относительные пути `CLAWGYM_CONFIG`, `CLAWGYM_VAR` и `CLAWGYM_WEB` считаются от рабочего каталога процесса, у `npm run demo` — от корня репозитория. `CLAWGYM_HOME` и `CLAWGYM_DATA` с 28 октября 2026 года не поддерживаются.

## Хранение

Решение владельца от 28 октября 2026 года: справочники и изменяемые данные лежат в двух независимых каталогах, у каждого своя переменная окружения.

| Каталог | Переменная | По умолчанию | Что лежит | Кто пишет |
| --- | --- | --- | --- | --- |
| Справочники | `CLAWGYM_CONFIG` | `config/` | `contracts/ cases/ solutions/ baskets/ runs/ agents/ models/ metrics/ templates/`; `data/`, если заглушки ссылаются на файлы. Состав — раздел «Файлы настроек» | Человек. Сам ClawGym пишет сюда только командой `import-tools` (`contracts/tools.json`). Редакторы в интерфейсе — следующий этап |
| Данные | `CLAWGYM_VAR` | `var/` | `results/run-NNNN/` — прогоны; `sessions/m-NNNN.json` и `m-NNNN.http.json` — ручные сессии; `operators.json` — журнал тестовых операторов: через какие прогоны и сессии прошёл каждый; `counters.json` — последние номера; `secret.json` — секрет `request_ref`, если не задан `REQUEST_REF_SECRET` | ClawGym во время работы |

- Каталоги не могут совпадать или лежать один в другом, иначе стенд не запустится. Так синхронизация одного каталога не захватит файлы другого.
- Если задана старая переменная `CLAWGYM_HOME` или `CLAWGYM_DATA`, стенд тоже не запустится и подскажет новые имена. Иначе результаты молча ушли бы в каталог по умолчанию, мимо постоянного тома.
- `web/` — часть кода, а не данных: в S3 его не синхронизируют.

**Версия формата записей.** `run.json`, журналы кейсов `executions/*.json`, ручные сессии и журнал операторов `operators.json` хранят версию формата в поле `format`; совместимость собрана в `src/results/format.ts`. Формат 2 — с 28 октября 2026 года: в снимке прогона полный SHA-256 файлов и настройки окружения, в истории оператора — и ручные сессии.
- Записи прежних версий ClawGym приводятся к текущему виду при загрузке. На диске они не меняются, пока ClawGym их не пересохранит.
- Запись более новой версии ClawGym — например, после отката образа — и повреждённый файл не загружаются и не перезаписываются. Причина видна в журнале стенда; после возврата на новую версию запись снова видна.
- Журналы HTTP-обменов хранятся без версии: их только показывают.

### Синхронизация с S3

План владельца на развёртывание: sidecar на rclone синхронизирует оба каталога в S3 и восстанавливает их при старте. Для этого ClawGym дорабатывать не нужно, но важен порядок. Ниже — рекомендации реализации; на стенде они не проверены.

1. **Восстановление — до старта ClawGym.** Его удобно делать init-контейнером, например `rclone copy`. ClawGym читает прогоны, сессии, счётчики и секрет один раз при старте. Если он запустится раньше восстановления, то не увидит прежних прогонов и создаст новый секрет. Тогда прежние `request_ref` перестанут сходиться, а выгрузка затрёт в S3 сохранённые `counters.json` и `secret.json`.
2. **Выгрузка — из пода в S3, у каждого каталога свой префикс**, например `s3:clawgym/config` и `s3:clawgym/var`. Встречная загрузка во время работы может подменить файл, который ClawGym как раз пишет.
3. **Временные файлы.** Атомарная запись создаёт рядом `*.tmp`; их стоит исключить: `--exclude "*.tmp"`.
4. **Удаление.** Прогоны и сессии удаляются в интерфейсе. `rclone sync` удалит их и в S3, `rclone copy` — оставит. Выбор за владельцем.
5. **Остановка.** По SIGTERM ClawGym сразу сохраняет отложенные изменения и дописывает начатые файлы. Последнюю выгрузку лучше делать после остановки ClawGym.
6. **Один экземпляр на префиксы.** Два пода с общим `var` выдадут одинаковые номера прогонов.
7. **Правка справочников в S3.** Пока редакторов нет, справочники правят файлами. Если правку загрузить прямо в S3, её затрёт выгрузка `config/` из пода. Нужно выбрать одно из двух: справочники только восстанавливаются из S3 и из пода не выгружаются, или их правят только в поде. Перечитать справочники без перезапуска — «Проверить файлы снова» или `POST /api/config/reload`.

## Файлы настроек

Настройки задаются только файлами; редакторы — следующий этап. Все файлы лежат в каталоге справочников `config/` (`CLAWGYM_CONFIG`); пути ниже считаются от него. Форматы с примерами — в [docs/FORMATS.md](docs/FORMATS.md).

| Каталог | Что лежит |
| --- | --- |
| `contracts/` | `tools.json` — MCP-инструменты, обёртка результата и тексты ошибок; `start-message.txt` — шаблон стартового сообщения; `tool-defaults.yaml` — ответы по умолчанию |
| `cases/` | Кейс: ситуация, факты, заглушки инструментов (из них же собирается стартовое сообщение), общий эталон, каталог уроков. Кейсы можно раскладывать по подкаталогам, например `cases/cards/`; файл или папка с именем на `_` пропускаются |
| `solutions/<кейс>/` | Решение: ссылка на кейс, цель и инструкция LLM-оператору |
| `baskets/` | Корзина: тип `training` или `checking`, фиксированный порядок решений, настройки curator |
| `runs/` | Настройка прогона: корзина, агент, модели оператора и оценки, продолжение на тестовом операторе (`continueFrom`), метрики, лимиты, повторения |
| `agents/` | REST-подключение агента: запрос, разбор ответа, команды, метка модели |
| `models/` | Модели LLM-оператора и оценки |
| `metrics/` | Выбор и параметры встроенных расчётов |
| `templates/`, `data/` | Шаблон тела запроса агенту (`aefclaw-a2a-message.json`); JSON-ответы заглушек (`result.file`), если они вынесены в файлы |

После правки файлов нажмите «Проверить файлы снова» в интерфейсе или вызовите `POST /api/config/reload`. Запущенный прогон работает со снимком настроек, сохранённым при старте, в том числе с контрактом инструментов. Исключение — `tools/list`: агент получает его из текущих настроек. Если `contracts/tools.json` изменился, пока прогоны идут или ждут в очереди, в журнале стенда появится предупреждение.

`run` поднимает сервис (MCP нужен агенту), выполняет прогон без интерфейса и печатает итоги. `--continue N` — продолжить на тестовом операторе прогона N, `--continue new` — новый оператор; без ключа — как в файле прогона.

### Инструменты со стенда оркестратора

`import-tools` снимает `tools/list` с MCP оркестратора и записывает `contracts/tools.json`:
- поля MCP (`name`, `title`, `description`, `inputSchema`, `annotations`) — из ответа как есть;
- пометки ClawGym (`requiresConfirmation`, `kind`, `enabled`, `terminal`) переносятся из текущего контракта;
- новые инструменты — информационные, без подтверждения и не терминальные, команда их перечисляет.

```bash
npm run import-tools -- --url http://<оркестратор>/mcp --header "x-task-id: clawgym-import"
```

Можно передать сохранённый ответ `tools/list`, например вывод `curl`:

```bash
npm run import-tools -- --file tools-list.json
```

С ключом `--check` команда ничего не пишет, а сверяет контракт с оркестратором: печатает добавленные, убранные и изменённые инструменты и завершается с кодом 1 при расхождении. Это проверка `drift-check` перед прогоном.

## Удаление прогонов и сессий

В интерфейсе удалить можно:

- завершённый, остановленный или упавший прогон — иконкой в таблице «Завершённые» или кнопкой «Удалить» на странице прогона;
- закрытую ручную сессию — иконкой в списке сессий или кнопкой «Удалить» на странице сессии.

Удаление спрашивает подтверждение и необратимо. Вместе с прогоном удаляется его каталог `var/results/run-NNNN/`, с сессией — файлы `var/sessions/m-NNNN.json` и `m-NNNN.http.json`.

Что удалить нельзя и что остаётся:

- прогон в очереди или в работе: сначала уберите его из очереди или остановите;
- активную сессию: сначала завершите её;
- скиллы тестового оператора остаются в агенте; прогоны, продолжившие его оператора, хранят историю у себя, но продолжить на нём из интерфейса больше нельзя — только в ручном режиме по `x-a2a-sender-id`;
- номера удалённых прогонов и сессий повторно не выдаются.

## Тестовый оператор

Решение владельца от 27 октября 2026 года: модель агента, стартовые и выученные скиллы живут внутри агента. Модель и стартовые скиллы меняются только сборкой, выученные — обучением. ClawGym их пока не меняет и не забирает:

- нет выбора версии набора скиллов и модели агента;
- нет установки и выгрузки скиллов, версий наборов и контроля неизменности набора.

Скиллы привязаны к тестовому оператору — `x-a2a-sender-id`:

- **Новый оператор** начинает со стартовых скиллов сборки агента.
- **Продолжение.** Прогон идёт на операторе прошлого завершённого прогона того же агента, с выученными там скиллами. В файле прогона это `continueFrom: <настройка>` — последний завершённый прогон этой настройки. При запуске можно выбрать другой прогон или нового оператора.
- **Проверка** не отправляет `/case-capture` и `/skill-curator`, поэтому скиллы оператора не меняет.
- **Что сделал curator** видно по строке результата: сколько кейсов разобрано, сколько скиллов создано и обновлено. Сами файлы остаются в агенте.

Схема аналитика: проверка на новом операторе → обучение → та же проверка на обученном операторе. В сравнении условия различаются только тестовым оператором. Готовые файлы: `demo-check` → `demo-train` → `demo-check-trained`, на стенде — `stand-check` → `stand-train` → `stand-check-trained`.

Сравнение сверяет полный SHA-256 каждого входного файла и настройки окружения: стартовое сообщение, заглушки по умолчанию, файлы ответов, шаблон запроса, адрес агента, модели и таймауты. В строке сравнения видно, что различается. Перечень и правила — `docs/CONTRACTS.md`, правило 20.

У оператора один диалог. Решение владельца от 28 октября 2026 года — подробности в `docs/CONTRACTS.md`, правило 8:

- **Резерв.** Оператор занят от запуска прогона или ручной сессии до их конца. Второй запуск на нём отклоняется, даже если обе кнопки нажаты одновременно.
- **История — по журналу оператора** `var/operators.json`: все прогоны и ручные сессии, через которые он прошёл. Прогон, выбранный для продолжения, задаёт оператора, а не его прошлое состояние: отката скиллов нет. Если после выбранного прогона оператор прошёл другие, при запуске видно предупреждение.

Выгрузку скиллов, например через ClawScope, отложили на потом.

## Прерванный ход

Ожидание ответа агента ограничивают только таймауты ClawGym: `TURN_TIMEOUT_MS` на реплику и свои — на служебные команды. Запросы к агенту идут через `node:http`. Встроенный `fetch` обрывал ожидание заголовков ответа на 300 с, а шлюз AEFClaw в режиме `sync` отдаёт их только в конце хода. Так обрывались и долгие ходы, и `/skill-curator` (разбор прогона владельца, 27 октября 2026 года).

Если ClawGym перестал ждать ответа, хотя запрос до агента дошёл, — по таймауту, из-за обрыва или остановки прогона, — агент может продолжать ход. Его сессия обрабатывает запросы оператора по очереди. Поэтому ClawGym:

- запоминает тестового оператора как занятого. Следующий запрос ему — `/reset`, реплика или команда — получает запас `AGENT_BUSY_WAIT_MS` и встаёт в очередь агента за прерванным. В журнале кейса видно, чего он ждёт, а обмен в журнале HTTP подписан «за прерванным запросом»;
- сразу отвечает ошибкой «Обращение остановлено на стенде.» на поздние вызовы инструментов прерванного хода: вызов с подтверждением не держит агента до `AGENT_MCP_TIMEOUT_MS`. В журнале кейса такие вызовы помечены «После завершения кейса»;
- если агент не освободился и с запасом, ставит кейсу статус «Агент занят прерванным запросом» и останавливает линию. Остальные кейсы получают «Не начат» с причиной: сбой не списывается на следующие кейсы.

Агент считается свободным, как только ответил на любой запрос. Сведения о прерванных запросах хранятся в памяти: после перезапуска ClawGym первый запрос ждёт обычный срок.

В демо долгий ход задаётся у fake-agent: `FAKE_AGENT_SLOW_ON` — регулярное выражение по тексту запроса, `FAKE_AGENT_SLOW_MS` — задержка. Очередь оператора в это время занята, как у шлюза.

## Метрики аналитика M1 и M2

Метрики взяты из документа аналитика «Аналитика оценки качества обучения агента» (ред. 22.10.2026). Владелец решил их применять 27 октября 2026 года. Тестовый датасет прогоняется до и после обучения, сравниваются ΔM1 и ΔM2:

- **M1** — macro-F1 класса финального действия. Классы: ответ клиенту и закрытие, экспертиза, запрос информации у клиента, инструкция оператору. Рядом — accuracy и матрица ошибок. Незавершённые кейсы в M1 не входят и считаются отдельно.
- **M2** — среднее по кейсам case_score = 0,5 · F1_tools + 0,5 · A_judge:
  - F1_tools считается по минимально достаточному набору инструментов эталона, порядок не важен. До 3 вызовов одного инструмента считаются одним, с 4-го вызова — лишние.
  - A_judge — судья три раза сравнивает итоговый текст агента с эталонным. A — доля ответов «соответствует»: 0, ⅓, ⅔ или 1.

В кейсе нужны `reference.finalClass`, `reference.tools` и эталонный текст `reference.finalText`; без `finalText` берётся `answer`. Подробнее — [docs/FORMATS.md](docs/FORMATS.md). В `metrics/builtin.yaml` задаются:

- веса;
- правило дубликатов;
- число прогонов судьи;
- соответствие класса инструментам.

Где смотреть:

- **Результат прогона** — в проверке плитки M1 и M2 идут первыми. Ниже — матрица ошибок M1, в таблице решений — колонка «M1 · M2».
- **Разбор кейса** — класс агента и эталон, F1 по каждому инструменту, вердикты судьи с обоснованием, итоговый и эталонный тексты.
- **Сравнение** — ΔM1, ΔM2 и case_score каждого кейса A → B.

**Терминальные инструменты меняют условия сравнения.** С 28 октября 2026 года кейс заканчивается, как только выполнен терминальный инструмент (`docs/CONTRACTS.md`, правило 21), а LLM-оператор работает на подсказке `operator-v2`. С прогонами до этого изменения сравнение покажет разные подсказки оператора. Пару «до и после обучения» прогоните заново, обе половины — на одной версии ClawGym.

M1 в демо различает «до» и «после» на кейсе `card-hold-amount`: клиент видит заблокированную, но не списанную сумму по карте.

- Стартовый скилл сборки fake-agent ведёт этот кейс как спорную операцию и выставляет экспертизу. Это неверный класс: эталон — ответ клиенту и закрытие.
- В обучении оператор отклоняет экспертизу и объясняет правило. Curator переносит урок в скилл тестового оператора, и после обучения агент отвечает клиенту и закрывает кейс.

Итог: M1 0,73 → 1,00, accuracy 0,75 → 1,00, в матрице ошибок до обучения — «экспертиза вместо ответа». В остальных кейсах класс верен до и после. Так же устроен датасет аналитика: пока все финалы в нём — ответ клиенту, и M1 различает версии только на кейсах, где агент ошибается с финалом.

## Журнал HTTP-обменов

Стенд записывает каждый HTTP-обмен с агентом в обе стороны и вызовы моделей:

- запросы ClawGym к агенту: `/reset`, стартовое сообщение, реплики оператора или человека, `/case-capture`, `/skill-curator`;
- запросы агента к MCP-серверу ClawGym с `x-task-id` кейса;
- вызовы LLM-оператора и LLM-оценки — что уходит в GigaChat и что приходит (просьба владельца от 27 октября 2026 года). Подписи: «LLM-оператор · конец хода», «LLM-оператор · подтверждение <инструмент>», «LLM-оценка · критерии ответа», «LLM-оценка · эталонный текст, прогон N из 3». Каждая HTTP-попытка — отдельный обмен: повтор после 429 или 5xx подписан «повтор N», повторный запрос после ответа не в формате — «переспрос формата».

У обмена есть метод, адрес, заголовки, тело запроса, статус, заголовки и тело ответа, время и длительность.

Где смотреть:

- **Разбор кейса** — вид «HTTP-обмены» с фильтром по направлению: к агенту, к MCP, к LLM. У событий журнала есть ссылка «HTTP» — у реплик, вызовов инструментов, решений оператора и оценок. У обмена — обратные ссылки на событие и ответ агента.
- **Ручная сессия** — вкладка «HTTP-обмены». Удерживаемый вызов MCP виден сразу, ответ появляется после решения. Вызовы LLM-оценки при завершении сессии — там же.
- **Результат прогона** — у прохода curator обмены `/reset` и `/skill-curator`.
- **Прогоны** — «Журнал стенда»: запросы MCP без привязки к кейсу, например `initialize`, `notifications/initialized` или вызов с неизвестным `x-task-id`.

Секреты скрываются:

- значения заголовков, в имени которых есть `auth`, `token`, `secret`, `key`, `passw`, `cookie`, `signature` или `credential`: например, `Authorization`, `X-Api-Key`, `Set-Cookie`;
- заголовки, подставленные из окружения через `${env:NAME}`, — при любом имени, и у агента, и у модели;
- токен модели в `Authorization`; клиентский сертификат GigaChat в заголовки не попадает вовсе;
- пароль в адресе и секретные параметры запроса.

Тела длиннее 256 КБ обрезаются с пометкой. Обмены сохраняются рядом с журналами: `var/results/run-NNNN/executions/<позиция>.http.json` и `var/sessions/m-NNNN.http.json`. Проходы curator хранят обмены в `run.json`. Запросы MCP без привязки держатся только в памяти.

## Сообщения агента в Markdown

Ответы агента показываются с разметкой Markdown (просьба владельца от 27 октября 2026 года): в разборе кейса, в ручной сессии, в текущем диалоге прогона и в итоговом тексте агента у метрик аналитика. Реплики LLM-оператора, человека и стартовое сообщение ClawGym остаются как есть: это то, что ушло агенту.

- **Что поддержано:** заголовки, списки с вложенностью и задачами `- [ ]`, цитаты, блоки кода, таблицы, разделитель, жирный, курсив, зачёркнутый `~~`, код в строке, ссылки и автоссылки. Перевод строки внутри абзаца сохраняется, как в чате.
- **Исходный текст.** У сообщения с разметкой есть переключатель «исходный текст»: сообщение так, как его прислал агент. Выбор держится, пока открыта страница, в том числе при обновлении ленты.
- **Безопасность.** HTML из сообщения не исполняется и виден как текст. Ссылки — только `http(s)` и `mailto`, открываются в новой вкладке; остальные, например `javascript:` или относительные, показываются текстом. Картинки не загружаются, вместо них ссылка.
- **Разбор** — `web/js/md.js`, без внешних библиотек: стенд работает в закрытом контуре. Текст длиннее 100 000 символов или с ошибкой разбора показывается как есть, вложенность глубже 12 уровней — текстом.

fake-agent отвечает в Markdown: проверки списком, ответ клиенту выделен. Так разметку видно в демо.
